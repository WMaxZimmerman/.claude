#+title: Azure Pipelines house rules (PL)

Read with =common.org=. Paths are repo-root-relative.

* Scope

Azure Pipelines YAML in any repo: pipeline definitions (=cicd-*.yml=, =pr-verify-*.yml= and their
kin), repo-wide reusable step, job and stage templates, per-project pipelines and step templates,
and any top-level pipeline file. Not Terraform (=terraform.org=), not Helm charts
(=helm-chart.org=), not Dockerfiles (=dockerfile.org=), not standalone shell scripts a pipeline
calls. When a path sits inside the pipeline tree but belongs to another stack — a chart values
file, a Dockerfile, a script for another CI system — the most specific path wins and that stack's
file governs it. YAML that is still Azure Pipelines YAML stays here, wherever it sits. What runs
after a pipeline hands off — a GitOps controller, an event-driven workflow engine — is not in
scope: the pipeline's job ends at the hand-off. Out-of-tree repos the pipeline depends on are
surfaced for impact only, never reviewed for shape.

* Calibration

Two pipeline families can coexist in one repo. Pick by deploy target, not by stack, and calibrate
findings inside each family against that family's conventions:

- *Azure-resource* — App Service / static web app / function app deploys through the built-in
  tasks (=AzureWebApp@1=, =AzureStaticWebApp@0=, and the like). Don't flag a working App Service
  pipeline for "not using the cluster path".
- *Cluster-via-GitOps* — image built with =buildctl=, pushed to a container registry (Harbor or
  similar), a release manifest pushed with =oras=, and an event (for example Argo Events'
  =RELEASE_READY=) firing the deploy — all through a shared build-push-deploy template; per-env
  values may live out of tree. Don't flag a working pipeline in this family for "not using
  =AzureWebApp@1=". PL-034..PL-054 and PL-058 apply only to this family, anchored on the shared
  template's own parameter declarations and steps, and apply to any pipeline that consumes it.

Fresh vs legacy:

- *Fresh greenfield YAML violating a best practice* → Smell by default, Bug for secrets /
  correctness / triggers that won't fire / conditions that mask production failures.
- *Long-standing legacy patterns shared across multiple pipeline files* (stale path filters,
  inlined steps that pre-date a template, missing =**/*.md= excludes on a few older =cicd-*.yml=)
  → mention once at the top (CM-005), not per file.
- *Mixing old and new in fresh code* (a brand-new =pr-verify-*.yml= with correct path filters
  that inlines a step the rest of the repo gets via template; a new step template with typed
  params next to siblings copied unchanged) → Smell.
- *A targeted edit to a legacy file* that follows the file's existing style for minimum diff →
  not a finding.
- When in doubt whether a file is fresh or legacy — or which family it belongs to — ask before
  reviewing.

Not findings: the =<verb>-<scope>-<artifact>.yml= naming convention itself; the repo's chosen
agent image; the repo's established service connection and deployment environment names; a tool
version pin the repo contract records as deliberate; the =AzureCLI@2= =addSpnToEnvironment: true=
+ =setvariable ARM_*= shape in a login template (the documented pattern for handing the service
principal to Terraform); the two-stage call pattern (dev / prod via two =template:= calls into the
shared build-push-deploy template); mixed pools on cluster-family pipelines (verify jobs on a
Microsoft-hosted =vmImage=, deploy stages on a self-hosted per-environment pool — deploy needs
cluster reachability); the repo's per-environment pool, environment, and domain naming in the
cluster family; Azure-resource and cluster-family pipelines coexisting in one tree. The
=0.0.0.0= / =0.0.0.0= "Allow Azure services" SQL firewall rule surfacing in a pipeline-supplied
tfvars file — leave it alone (TF-008).

Confirm path-filter findings by globbing the included path against the repo before flagging — a
"stale path" finding that matches real files is noise.

Rules lifted from =mz-pipeline-writer='s house conventions with no reviewer rule yet carry Smell
severity unless the entry states otherwise.

* Secrets and exposure

** PL-001 — Secrets never echoed to logs

- *Severity:* Bug
- *Applies to:* all code
- *Rule:* Secrets echoed to logs (~echo $(SECRET_VAR)~, =Write-Host $env:SECRET=, =printenv= of a
  secret, printing =ARM_*= values).
- *Not a finding:* none.
- *Precedent:* none yet

** PL-002 — Secrets never passed as positional command-line args

- *Severity:* Bug

- *Rule:* Secrets passed as positional command-line args to scripts (visible in process listings
  and logs). Pipe via stdin or env var with masking instead.
- *Not a finding:* none.
- *Precedent:* none yet

- *Not a finding:* the =AzureCLI@2= =addSpnToEnvironment: true= + =setvariable ARM_*= shape in a

* Correctness and runtime hazards

** PL-006 — =pr-verify-*.yml= has a =pr:= block mirroring its Build Validation policy filter

- *Severity:* Bug
- *Applies to:* all code
- *Rule:* =pr-verify-*.yml= with =trigger: none= and no =pr:= block, or a =pr:= block whose paths
  do not mirror the Build Validation branch policy's path filter. On an Azure Repos Git repo the
  YAML =pr:= trigger is not evaluated, and the policy's own path filter (leading-slash form,
  =/src/<project>/*=) decides when the check runs — it is authoritative. The =pr:= block is the
  in-repo record of that filter, so a missing or non-mirroring block misroutes readers and
  reviewers about what gates the PR. A change whose PR enforcement depends on a policy states the
  policy's path filter (new or changed) as part of the change, since the policy lives outside the
  repo.
- *Not a finding:* none.
- *Precedent:* a =pr-verify-*.yml= with a top-level =pr:= block whose =pr.paths= match the
  policy's path filter.

** PL-007 — =pr-verify-*.yml= has =trigger: none=

- *Severity:* Bug
- *Applies to:* all code
- *Rule:* =pr-verify-*.yml= with =trigger:= other than =none= — re-runs on every push to the
  source branch on top of the PR runs. The YAML CI =trigger:= is honoured on Azure Repos Git; PR
  runs come from the Build Validation policy (PL-006), not from =pr:=.
- *Not a finding:* none.
- *Precedent:* a =pr-verify-*.yml= with top-level =trigger: none=.

** PL-008 — =cicd-*.yml= triggers on the integration branch with =pr: none=

- *Severity:* Bug
- *Applies to:* all code
- *Rule:* =cicd-*.yml= without =trigger.branches.include= naming the integration branch, or with
  =pr: none= missing on a CI/CD pipeline that should not double-fire.
- *Not a finding:* none.
- *Precedent:* none yet

* Reuse and structure

** PL-019 — Reuse templates; don't inline

- *Severity:* Smell for fresh code
- *Applies to:* new or touched code
- *Rule:* Inlined steps that already exist as a template (a repo-wide template or a per-project
  step template). Reference via =template:= with parameters. If inlining, justify why no template
  fits.
- *Not a finding:* long-standing inlined steps shared across multiple pipelines that pre-date a
  template extraction — project-level drift, surface once at the top.

** PL-021 — Step template parameters are typed

** PL-022 — Required parameters have no =''= default

- *Severity:* Smell
- *Applies to:* new or touched parameter declarations
- *Rule:* Required parameters declared with a default of =''= (silent-failure shape) when they
  have no sensible default. Defaults only for parameters that have a sensible one; required
  parameters listed without a default.
- *Not a finding:* pre-existing =default: ''= declarations on untouched lines — legacy drift,
  tracked as tech debt. A touched declaration must be fixed; a required parameter with no
  sensible default is listed without one.
- *Precedent:* none yet

** PL-058 — =envName:= disagrees with the stage's environment on a cluster-family deploy stage

* Writer conventions (from =mz-pipeline-writer=, no reviewer rule yet)

** PL-055 — File-level shape: =parameters:= first, no top-level =name:= on step templates

- *Severity:* Smell
- *Applies to:* new or touched files
- *Rule:* =parameters:= block first (with defaults), then =steps:= (or =jobs:=, =stages:=). No
