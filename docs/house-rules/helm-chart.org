#+title: Helm chart house rules (HC)

Read with =common.org=. Paths are relative to the root of the repo under review.

* Scope

Helm charts in any repo: each chart's =Chart.yaml=, =values.yaml= and =templates/=, the committed
per-environment overlays (=values.<env>.yaml=), and any in-repo provisioning or secrets charts. Read
alongside the deploy contract — whatever packages, pushes and installs the chart (a workflow or
pipeline job: chart name, registry push path, release name, namespace, the per-environment =-f=
overlay, the =--set= image tags) and any lint gate. Not pipeline YAML (=pipeline.org=), not
Terraform (=terraform.org=), not the EF migration bundle or entity model (=csharp.org=) — only the
hook-Job shape. Not cluster state or =kubectl get= output.

A values-only directory outside the chart tree — overlays for a chart that lives elsewhere, applied
by a pipeline or by hand — is also covered, but contains no chart, so only the values-shaped rules
reach it: secrets and exposure (HC-001, HC-002), key/default hygiene, and HC-042's Suggestion
grading for comments. Every template-shaped rule — =Chart.yaml= shape, the per-workload template
split, label keys, hook weights, the Secret/ConfigMap split, =existingSecret= — has no subject
there. Never review the out-of-tree chart those values feed; review only the values.

* Calibration

- Single severity ladder unless the repo has a legacy chart. The repo's best-shaped chart is the
  reference shape and the baseline for every "does this match precedent" finding. Where it doesn't
  establish a policy, apply standard Helm / K8s practice.
- Not findings — house style: the one-chart-per-service layout, the per-workload template split,
  =<workload>-<kind>.yaml= naming (shared templates use the bare kind), the
  =app: <service>-<workload>= label key, =apiVersion: v2= / =type: application= in =Chart.yaml=, a
  top-level =appVersion: "1.0.0"= literal (CI overrides =version= / =appVersion= at package time),
  the =pre-install,pre-upgrade= + weight =-5= + =before-hook-creation,hook-succeeded=
  migration-hook pattern, a static K8s Secret for a service that is not AAD-backed (HC-006), the
  lack of =allowPrivilegeEscalation: false= / =capabilities.drop: ["ALL"]= /
  =readOnlyRootFilesystem: true= on an existing chart (not house policy; HC-015), the lack of
  =values.schema.json= (not adopted; revisit if external override files start typoing keys).
- Charts never deploy themselves. Read the deploy contract named in Scope before ruling on any
  chart-name, image-repository, namespace or overlay finding (HC-043 through HC-046).
- A values file for a CI runner that is rebuilt on every push may use =image.tag: "latest"= with
  =pullPolicy: Always= deliberately; where the repo contract records that exception it is not an
  HC-009 / HC-011 finding. A values key that exists to feed per-cluster settings to a runner or
  workflow, and appears nowhere else, is the contract working, not a gap. A values file that holds
  only secret-store paths, roles and mounts — never secret values — passes HC-001; a literal
  credential there is still a Bug.
- When in doubt whether a values key is consumed: glob the chart's =values.yaml= keys against its
  templates — mismatches between values defaults and template references are a recurring bug
  source.
- Rules lifted from the Helm chart writer's house conventions with no reviewer rule yet carry Smell
  severity unless the entry states otherwise.

* Secrets and exposure

** HC-001 — No hardcoded secrets in =values.yaml= or templates

- *Severity:* Bug
- *Applies to:* all code
- *Rule:* Hardcoded secrets, connection strings, tokens, keys, passwords in =values.yaml= or
  templates. Use the Secret + =existingSecret= pattern, or Workload Identity for AAD-backed services.
- *Not a finding:* none.
- *Precedent:* none yet

** HC-002 — Sensitive values live in a Secret, not a ConfigMap

- *Severity:* Bug
- *Applies to:* all code
- *Rule:* Sensitive values in a ConfigMap instead of a Secret. ConfigMaps are not encrypted at rest
  by default and are world-readable within the namespace. Non-sensitive →
  =<workload>-configmap.yaml=, sensitive → =<workload>-secret.yaml=, both =envFrom='d.
- *Not a finding:* none.
- *Precedent:* none yet

** HC-003 — Every Secret template has the =existingSecret= escape hatch

- *Severity:* Smell
- *Applies to:* all code
- *Rule:* A Secret template missing the =existingSecret= escape hatch
  (={{- if not .Values.<workload>.secrets.existingSecret }}= gate).
- *Not a finding:* none.
- *Precedent:* a Secret template whose opening =if= gates on
  =.Values.<workload>.secrets.existingSecret=.

** HC-004 — =envFrom= Secrets can be swapped for an external one

- *Severity:* Smell
- *Applies to:* all code
- *Rule:* Pod with =envFrom= referencing a Secret but the chart provides no way to swap to an
  externally-managed one.
- *Not a finding:* none.
- *Precedent:* a container =envFrom= whose =secretRef= branches on
  =.Values.<workload>.secrets.existingSecret=.

** HC-005 — =secrets.*= values default to =""=

- *Severity:* Bug
- *Applies to:* all code
- *Rule:* =secrets.databasePassword= / =secrets.<X>= shipped in =values.yaml= as anything other than
  =""= default. (Stated under both Secrets and Values shape; one rule here.)
- *Not a finding:* none.
- *Precedent:* none yet

** HC-006 — AAD-backed services use Workload Identity on the ServiceAccount

- *Severity:* Bug
- *Applies to:* all code
- *Rule:* ServiceAccount talking to an AAD-backed Azure service (Key Vault, Storage, Service Bus,
  MSSQL via AAD) without the =azure.workload.identity/client-id= annotation. The federated identity
  credential lives in Terraform — the writer surfaces the missing Terraform side when adding the
  first Workload-Identity-bound chart.
- *Not a finding:* a static K8s Secret for a service that is not AAD-backed (for example a Postgres
  password or S3-compatible keys).
- *Precedent:* none yet

** HC-007 — Workload Identity pods carry the =use= label

- *Severity:* Bug
- *Applies to:* all code
- *Rule:* Pod consuming Workload Identity without the =azure.workload.identity/use: "true"= label.
- *Not a finding:* none.
- *Precedent:* none yet

** HC-008 — No new static Secret where Workload Identity fits

- *Severity:* Smell
- *Applies to:* new or touched code
- *Rule:* New static K8s Secret introduced for a service that is AAD-backed when Workload Identity
  would fit. Surface, confirm the exception is intentional.
- *Not a finding:* the non-AAD exception (HC-006).
- *Precedent:* none yet

** HC-014 — Workloads set =serviceAccountName=

- *Severity:* Smell
- *Applies to:* all code
- *Rule:* Deployment / Job missing =serviceAccountName=. The default SA shouldn't run workloads. One
  ServiceAccount per chart (=serviceaccount.yaml=), gated on =.Values.serviceAccount.create=, named

- *Not a finding:* none.
- *Precedent:* none yet

** HC-015 — =securityContext.runAsNonRoot: true=

- *Severity:* Smell
- *Applies to:* all code
- *Rule:* Deployment / Job / Pod missing =securityContext.runAsNonRoot: true=. Surface if a base
  image actually requires root. Pod-level =fsGroup=, container-level =runAsNonRoot: true= +
  =runAsUser= matching the image's user (for example 101 for nginx-unprivileged).
- *Not a finding:* an existing chart's lack of =allowPrivilegeEscalation: false= /
  =capabilities.drop: ["ALL"]= / =readOnlyRootFilesystem: true= — not house policy; flag as
  Suggestion on new charts if at all, never on an existing one. The writer surfaces adding them in
  its proposal for a new chart so the user can opt in.
- *Precedent:* none yet

* Per-environment values contract

** HC-043 — Values key changes are matched in the per-environment values files

- *Severity:* Bug
- *Applies to:* all code
- *Rule:* Chart adds, removes, or renames a values key without the matching change in the committed
  per-environment overlays (=values.<env>.yaml= for an application chart, or wherever the deploy
  contract keeps a provisioning chart's per-environment values). The overlay does not auto-rename:
  the deploy either falls back to the =values.yaml= default silently or fails, and an =--atomic=
  install rolls back. Even a single renamed key matters, and every environment file needs it, not
  just =dev=.
- *Not a finding:* a key with no per-environment override in any overlay file. A provisioning
  chart's out-of-cluster effects themselves. Per-environment values that live out of tree — the
  same rule holds, but that content is out of tree, so surface impact only.
- *Precedent:* none yet

** HC-044 — =Chart.yaml= name matches the deploy's chart name

- *Severity:* Bug
- *Applies to:* all code
- *Rule:* Chart name in =Chart.yaml= doesn't match the name the deploy packages and pulls by (the
  chart-name variable or parameter in the workflow or pipeline that pushes and installs it). A
  mismatch means the deploy cannot find the chart.
- *Not a finding:* the chart name differing from the release name or the namespace — a deploy may
  keep a legacy release or namespace identity while the chart is renamed.
- *Precedent:* none yet

** HC-045 — Image =repository= matches the images the build pushes

- *Severity:* Bug
- *Applies to:* all code
- *Rule:* Image =repository= in =values.yaml= doesn't match what the build actually pushes (the
  registry project and image-name variables or parameters in the build workflow or pipeline). The
  build pushes to one path and the chart pulls from another; the pods land in =ImagePullBackOff= and
  an =--atomic= install rolls the release back.
- *Not a finding:* the =tag= field's default when the deploy overrides the image tags with =--set=.
- *Precedent:* none yet

** HC-046 — Deploy namespace matches what the chart expects

- *Severity:* Bug
- *Applies to:* all code
- *Rule:* The namespace the deploy installs into (the namespace variable or parameter passed as
  =--namespace=) doesn't match what the chart expects. Templates read ={{ .Release.Namespace }}=
  rather than hardcoding, so a wrong namespace installs a second, silently parallel release instead
  of failing. Surface it even though the value is deploy-side.
- *Not a finding:* templates that reference ={{ .Release.Namespace }}= rather than a values key —
  that is the house pattern, and the namespace is supplied by the deploy.
- *Precedent:* none yet

* Writer conventions (no reviewer rule yet)

** HC-055 — =values.yaml= ordering and =camelCase= keys

- *Severity:* Smell
- *Applies to:* new or touched =values.yaml=
- *Rule:* Top-level shared blocks first (=imagePullSecrets=, =serviceAccount=, =securityContext=),
  then per-workload blocks (=api=, =web=, ...), then shared infrastructure (=ingress=), then
  scheduling escape hatches (=nodeSelector=, =tolerations=, =affinity=). Values keys are
  =camelCase= (=apiBaseUrl=, =presignedUrlExpirySeconds=, =frameAncestors=). Defaults are neutral;
  per-environment overrides come from the per-environment overlays.
- *Not a finding:* none.
- *Precedent:* none yet

** HC-056 — Env vars are =<APP>__<SECTION>__<KEY>=

- *Severity:* Smell
- *Applies to:* new or touched ConfigMaps / Secrets
- *Rule:* Env var names use double-underscore segments in .NET configuration style
  (=<APP>__<SECTION>__<KEY>=).
- *Not a finding:* none.
- *Precedent:* none yet

** HC-057 — =envFrom= order: =configMapRef= then =secretRef=

- *Severity:* Smell
- *Applies to:* new or touched workloads
- *Rule:* Workloads =envFrom= both the ConfigMap and the Secret — =configMapRef= first, then

- *Not a finding:* none.

** HC-058 — Probe shape: TCP by default, =httpGet= for a known static path

- *Severity:* Smell
- *Applies to:* new or touched workloads
- *Rule:* TCP socket probes by default; =httpGet= against a static path (=/index.html= for Blazor
  WASM) when the workload serves a known unauthenticated endpoint. =periodSeconds: 10= readiness,
  =30= liveness.
- *Not a finding:* none.
- *Precedent:* an API container probed with =tcpSocket=, and a static web container probed with
  =httpGet= on =/index.html=.

** HC-059 — Resource names are =<service>-<workload>=

  =myapp-api-migrate=), matching the =app:= label (HC-026).
- *Not a finding:* none.
