#+title: Terraform house rules (TF)

Read with =common.org=. Paths are repo-root-relative.

* Scope

Terraform / HCL in any repo: the root module and its child modules, whatever file layout the
project has established for them (TF-031), their =*.tpl= templates, and per-environment =*.tfvars=
files. A rule written for one cloud names that cloud in its =Applies to= and has no subject in a
project that does not use it; the rest apply to any provider. Apply runs from the project's CI or
deployment automation, never from a developer machine. Not CI YAML — =pipeline.org= for Azure
Pipelines, =github-actions.org= for GitHub Actions, whichever the repo uses — and not Helm charts
(=helm-chart.org=). A file the repo contract marks as dormant or out of scope is left alone.

* Calibration

Fresh vs legacy:

- *Fresh greenfield tf violating a best practice* → Smell by default, Bug for security /
  data-loss / public-exposure issues. Don't soften severity because surrounding modules have the
  same gap.
- *Long-standing legacy patterns shared across modules* (every storage account is publicly
  addressable, tags are sparse and inconsistent, no resource has a =tags= block) → mention once at
  the top as a project-level migration opportunity (CM-005), not per file.
- *Mixing old and new in fresh code* (a new module with ~tags = { ... }~ on some resources but not
  others; new code adding =prevent_destroy= to one stateful resource and not its sibling) → Smell.
- *A targeted edit to a legacy file* that follows the file's existing style for minimal diff →
  not a finding.
- When in doubt whether a file is fresh or legacy, ask before reviewing.

Not findings: the repo's provider choice, its modular layout, a per-environment tfvars split, and
the dev-default-in-=variables.tf= + prod-override pattern — all house style. Descriptive-but-verbose
resource block names — house style. Dashboard template content is house style (TF-030 covers only
clearly broken content).

Terraform / Helm boundary, where a project deploys its workloads with Helm: the split the project
has established between the two is the one graded. In a project that has established none,
Terraform owns anything cluster-scoped or platform-shared — the cluster itself, the container
registry, federated identity credentials, secret-store entries (Key Vault on Azure), messaging,
storage accounts, databases — and workloads (Deployments, Services, ConfigMaps, Secrets, and the
routing resources of the chart's routing API) live in the Helm chart (=helm-chart.org=). Don't
flag tf for "should be in Helm" or chart files for "should be in tf".

Required wherever state would otherwise be lost: destroy protection on stateful production
resources (TF-010), and a recorded state move for an address refactor or a decommission (TF-012).
The mechanism is the one the project has established; in a project that has established none it
is ~lifecycle { prevent_destroy = true }~ for destroy protection, =moved {}= for address
refactors, and =removed {}= with ~lifecycle { destroy = true|false }~ for decommissioning.
Dashboards render through the mechanism the project has established;
=templatefile("${path.module}/dashboard.tpl", { ... })= is the default where it has established
none.

*Match the project's established choices.* The resource naming pattern, the file layout inside a
module, the destroy-protection and state-move mechanisms, the dashboard rendering mechanism, the
diagnostics destination, the secret store, and where the Terraform CLI version is pinned that a
project has established are the ones its Terraform is graded against. The choices this file names
— the =-${var.env}= name suffix with kebab-case and an area prefix, =main.tf= plus
per-resource-type files, =prevent_destroy=, =moved {}= / =removed {}=, =templatefile= dashboards,
a Log Analytics workspace as the diagnostics destination, Key Vault as the secret store, the CLI
version pinned in the pipeline — are the default only for a project that has established none. A
project has established a choice when its existing Terraform uses it. Fresh Terraform that brings
in a second shape beside the established one is the finding; one that follows the established
shape rather than this file's default is not. Moving such a project onto the default is a
migration asked for explicitly, never a review finding. A rule written for one cloud has no
subject in a project that does not use it, and its =Applies to= names that cloud. TF-001, TF-004
through TF-012, TF-017, TF-019, TF-020, TF-024, TF-027, TF-030 and TF-031 carry this scoping in
their own fields. It is separate from the fresh-vs-legacy calibration above, which stands as
written.

Rules lifted from =mz-terraform-writer='s house conventions with no reviewer rule yet carry Smell
severity unless the entry states otherwise.

* Secrets and exposure

** TF-001 — No hardcoded secrets in tf

- *Severity:* Bug
- *Applies to:* all code
- *Rule:* Hardcoded secrets, connection strings, keys, tokens, SAS URLs, account keys directly in
  tf files. Read them from the secret store the project has established, through its provider's
  data source — on Azure, Key Vault through =data "azurerm_key_vault_secret"= — or from variables
  the CI run supplies.
- *Not a finding:* none.
- *Precedent:* none yet

** TF-002 — Sensitive-shaped variables are ~sensitive = true~

- *Severity:* Smell
- *Applies to:* all code
- *Rule:* Sensitive-shaped variables (tenant IDs, client object IDs, secret values) declared
  without ~sensitive = true~.
- *Not a finding:* none.
- *Precedent:* none yet

** TF-003 — Sensitive module outputs are ~sensitive = true~

- *Severity:* Bug
- *Applies to:* all code
- *Rule:* Module outputs that surface sensitive values (connection strings, primary access keys,
  secrets) without ~sensitive = true~.
- *Not a finding:* none.
- *Precedent:* none yet

** TF-004 — Least-privilege role assignments and KV access policies

- *Severity:* Smell
- *Applies to:* all code, on Azure (the =azurerm= provider)
- *Rule:* =azurerm_role_assignment= or =azurerm_key_vault_access_policy= granting more
  permissions than the use case requires (=Set= / =Delete= / =Purge= when only =Get= / =List= is
  needed).
- *Not a finding:* none.
- *Precedent:* none yet

** TF-005 — Role assignments scoped as narrowly as possible

- *Severity:* Smell
- *Applies to:* all code, on Azure (the =azurerm= provider)
- *Rule:* Role assignments scoped at subscription when resource-group or resource scope would
  suffice.
- *Not a finding:* none.
- *Precedent:* none yet

* Public network exposure

** TF-006 — Storage accounts restrict public network access

- *Severity:* Smell
- *Applies to:* fresh additions, on Azure (the =azurerm= provider)
- *Rule:* Storage accounts without explicit ~public_network_access_enabled = false~ or
  =network_rules= restricting access.
- *Not a finding:* existing public-network-access defaults on long-standing storage accounts —
  historical drift; surface once at the top.
- *Precedent:* none yet

** TF-007 — App Service, Function App, SQL Server, Key Vault not publicly addressable without justification

- *Severity:* Bug for fresh resources holding sensitive data; Smell otherwise
- *Applies to:* all code, on Azure (the =azurerm= provider)
- *Rule:* App Service, Function App, SQL Server, Key Vault publicly addressable without explicit
  justification or IP restrictions.
- *Not a finding:* none.
- *Precedent:* none yet

** TF-008 — No broad =azurerm_mssql_firewall_rule= source ranges

- *Severity:* Bug
- *Applies to:* all code, on Azure (the =azurerm= provider)
- *Rule:* =azurerm_mssql_firewall_rule= with broad source ranges — actual broad ranges like
  =0.0.0.0= to =255.255.255.255=.
- *Not a finding:* a ~start_ip_address = "0.0.0.0"~ / ~end_ip_address = "0.0.0.0"~ rule — the
  documented Azure "Allow Azure services" pattern, intentional. The same shape in a tfvars file
  the CI run supplies is also left alone.
- *Precedent:* none yet

** TF-009 — No wildcard inbound NSG rules on non-public-facing resources

- *Severity:* Bug
- *Applies to:* all code, on Azure (the =azurerm= provider)
- *Rule:* NSG rules with ~source_address_prefix = "*"~ or =0.0.0.0/0= on inbound for
  non-public-facing resources.
- *Not a finding:* none.
- *Precedent:* none yet

* State-management hygiene

** TF-010 — Stateful production resources carry destroy protection, =prevent_destroy= by default

- *Severity:* Smell
- *Applies to:* new stateful resources
- *Rule:* A stateful production resource (a database, a storage account that holds persistent
  data, a secret store such as a Key Vault) with no destroy protection. The protection is the
  mechanism the project has established; ~lifecycle { prevent_destroy = true }~ where it has
  established none (Calibration).
- *Not a finding:* destroy protection through the project's established mechanism rather than
  =prevent_destroy=.
- *Precedent:* an =azurerm_mssql_database= carrying ~lifecycle { prevent_destroy = true }~.

** TF-011 — Removing destroy protection needs a written rationale

- *Severity:* Bug unless the diff is explicitly part of a planned decommission
- *Applies to:* all code
- *Rule:* Removing destroy protection (=prevent_destroy=, or the project's established mechanism)
  from an existing stateful resource without a written rationale. The rationale is in
  =mz-terraform-writer='s Gate 1 plan or the pull-request description, never a comment in the tf,
  which is itself a CM-003 finding (TF-032).
- *Not a finding:* a planned decommission stated in =mz-terraform-writer='s Gate 1 plan or the
  pull-request description.
- *Precedent:* none yet

** TF-012 — =moved {}= / =removed {}= blocks are coherent

- *Severity:* Smell
- *Applies to:* all code; the blocks named are the default state-move mechanism, and a project's
  established mechanism is graded in their place (Calibration)
- *Rule:* New =moved {}= blocks pointing at addresses that don't exist in state, or =removed {}=
  blocks without a clear ~lifecycle { destroy = true|false }~ decision. Existing =moved= /
  =removed= blocks are a state-management contract — never squashed or reordered.
- *Not a finding:* none.
- *Precedent:* none yet

** TF-013 — No stale =import= blocks

- *Severity:* Smell
- *Applies to:* all code
- *Rule:* Manual =import= blocks left in code after import is complete.
- *Not a finding:* none.
- *Precedent:* none yet

* Module shape and variables

** TF-014 — Module variables are typed

- *Severity:* Smell
- *Applies to:* all code
- *Rule:* Untyped module variables (no =type=).
- *Not a finding:* none.
- *Precedent:* none yet

** TF-015 — Non-trivial variables carry =description=

- *Severity:* Suggestion
- *Applies to:* all code
- *Rule:* Module variables missing =description= when their purpose isn't trivial from the name.
- *Not a finding:* none.
- *Precedent:* none yet

** TF-016 — SKUs, sizes, regions are variables, not module literals

- *Severity:* Smell
- *Applies to:* all code
- *Rule:* Hardcoded SKUs, sizes, regions in module code that should be variables passed from the
  root.
- *Not a finding:* none.
- *Precedent:* none yet

** TF-017 — No tfvars drift between environments

- *Severity:* Smell
- *Applies to:* all code, in a project that splits its environments into per-environment tfvars
  files
- *Rule:* Variables present in one environment's tfvars file (for example =prod.tfvars=) but
  missing from another's (=dev.tfvars=) when both environments need an explicit value. Surface
  explicitly: name the variable, name which file is missing it. Writers make the asymmetry
  explicit in the Variable-file drift call-out.
- *Not a finding:* the pattern of dev-shape defaults in =variables.tf= + prod overrides — flag
  only when both environments genuinely need explicit values.
- *Precedent:* none yet

** TF-018 — New module variables are wired through from the caller

- *Severity:* Bug
- *Applies to:* all code
- *Rule:* A new variable added to a module's =variables.tf= but not wired through from the root
  module's call to that module — the caller hits a "value for input variable required" error.
  The root variable in the root =variables.tf= (with a default if appropriate) travels with it.
- *Not a finding:* none.
- *Precedent:* none yet

* Resource composition

** TF-019 — Log-producing resources have a diagnostic setting

- *Severity:* Smell
- *Applies to:* all code, on Azure (the =azurerm= provider)
- *Rule:* Missing =azurerm_monitor_diagnostic_setting= on resources that produce logs (App
  Service, Function App, SQL Database, Storage), pointed at the diagnostics destination the
  project has established — the module's Log Analytics workspace where it has established none.
- *Not a finding:* none.
- *Precedent:* none yet

** TF-020 — Cross-module workspace references are explicit

- *Severity:* Smell
- *Applies to:* all code, on Azure (the =azurerm= provider)
- *Rule:* Diagnostic settings pointed at workspaces in a different module without a clear
  cross-module reference.
- *Not a finding:* none.
- *Precedent:* none yet

** TF-021 — Tags are consistent within a module

- *Severity:* Smell
- *Applies to:* fresh inconsistency within a module
- *Rule:* Missing tags when other resources in the same module have them.
- *Not a finding:* sparse tagging across the codebase (a =product= tag on a few resources only)
  — known drift; surface project-level once at the top. When extending an existing module,
  matching the surrounding file is correct; tagging discipline is a project-level migration the
  user asks for explicitly.
- *Precedent:* none yet

** TF-022 — =for_each= over =count= for keyed resource sets

- *Severity:* Smell
- *Applies to:* new or touched code
- *Rule:* =count= used where =for_each= with a string key would be clearer (especially for
  resource sets that get added / removed / reordered).
- *Not a finding:* none.
- *Precedent:* none yet

** TF-023 — Implicit dependencies over rote =depends_on=

- *Severity:* Smell
- *Applies to:* new or touched code
- *Rule:* =depends_on= used where implicit reference dependencies would suffice. Rote
  =depends_on= listing every related resource is the smell.
- *Not a finding:* real ordering requirements that references can't express (a Key Vault access
  policy that must exist before another resource reads a secret).
- *Precedent:* none yet

* Provider and version pinning

** TF-024 — =required_version= present and matching the project's pinned CLI version

- *Severity:* Smell
- *Applies to:* all code; the CLI-version half applies where the project pins a Terraform CLI
  version — in its CI configuration by default, or wherever else it has established
- *Rule:* Missing ~terraform { required_version = "..." }~ at the root, or pinned versions that
  drift between local and the Terraform CLI version the project pins.
- *Not a finding:* none.
- *Precedent:* none yet

** TF-025 — Providers are pinned

- *Severity:* Smell
- *Applies to:* all code
- *Rule:* Missing =required_providers= block or unpinned provider versions.
- *Not a finding:* none.
- *Precedent:* none yet

** TF-026 — Provider bumps are their own change

- *Severity:* Smell
- *Applies to:* all code
- *Rule:* Bumping a provider version (or =required_version=) as a side effect of an unrelated
  change. Surface as a separate decision; if a feature genuinely requires a newer provider, the
  writer surfaces the bump in its proposal.
- *Not a finding:* none.
- *Precedent:* none yet

* Style and readability

- =TODO= / =FIXME= / =HACK= — CM-001.
- No comments at all — CM-003, restated for =*.tf= and =*.tfvars= in TF-032.

** TF-027 — Cloud-side names follow the project's naming pattern, =-${var.env}= suffix by default

- *Severity:* Smell
- *Applies to:* new or touched code
- *Rule:* A resource's cloud-side name that departs from the naming pattern the surrounding module
  and the project have established — environment marker, casing, prefix. Where they have
  established none: kebab-case, with the area prefix the surrounding module uses and a
  =-${var.env}= suffix (=<prefix>-sqlserver-${var.env}=, =ai-<prefix>-api-${var.env}=).
- *Not a finding:* a name that follows the project's established pattern rather than the default.
  On Azure, storage account names without dashes (=<prefix>appdocs${var.env}=) — Azure forbids
  dashes there; the environment marker still applies.
- *Precedent:* none yet

** TF-028 — Resource block names are =snake_case= and consistent

- *Severity:* Smell
- *Applies to:* new or touched code
- *Rule:* Resource block names not in =snake_case=, or wildly inconsistent within a module
  (=orders_sql_server=, =ai_orders_api= are the shape).
- *Not a finding:* descriptive-but-verbose block names — house style.
- *Precedent:* none yet

** TF-029 — Module variable order matches the caller

- *Severity:* Suggestion
- *Applies to:* new or touched code
- *Rule:* Module variables in a different order than the root module's call passes them —
  readability hit when scanning for parity.
- *Not a finding:* none.
- *Precedent:* none yet

** TF-032 — CM-003 in =*.tf= and =*.tfvars= files, tool directives excepted

- *Severity:* Smell
- *Applies to:* new or touched code only, in =*.tf= and =*.tfvars= files
- *Rule:* CM-003 applies — a =#= line, a =//= line, and a =/* */= block comment in a =*.tf= or
  =*.tfvars= file are all comments here. Name the resource, the variable, or the local so it reads
  without one, with design rationale moved to the pull-request description or the issue.
- *Not a finding:* one carve-out, and no other. A tool directive — a comment line that instructs a
  linter or scanner, such as ~# tflint-ignore: <rule>~, ~# checkov:skip=<id>:<reason>~,
  ~# trivy:ignore:<id>~ or ~#tfsec:ignore:<id>~ — is not a comment for this rule; whether the
  finding it suppresses was justified is graded on its own, not under CM-003.
- *Precedent:* none yet

* Dashboards

** TF-030 — Dashboard templates are flagged only when clearly broken

- *Severity:* Smell
- *Applies to:* all dashboard templates, in a project that renders dashboards from templates
- *Rule:* Malformed JSON or broken =${...}= references in a dashboard template. Dashboards stay in
  the module that owns them and render through the mechanism the project has established —
  =templatefile("${path.module}/dashboard.tpl", { ... })= where it has established none.
- *Not a finding:* style choices inside dashboards — house style.
- *Precedent:* none yet

* Writer conventions (from =mz-terraform-writer=, no reviewer rule yet)

** TF-031 — Resources land in the file matching their type

- *Severity:* Smell
- *Applies to:* new resources
- *Rule:* A new resource placed outside the file layout the module and the project have
  established. Where they have established none: module =main.tf= owns shared resources (a log
  workspace, common data lookups); everything else lands in the per-resource-type file (=app.tf=,
  =function.tf=, =keyvault.tf=, =database.tf=, =alerts.tf=, =dashboard.tf=,
  =storage-account.tf=), and a new resource-type file is created rather than dumping into
  =main.tf= when no existing file fits.
- *Not a finding:* a resource placed by the project's established layout rather than the default.
- *Precedent:* none yet
