#+title: Dockerfile house rules (DK)

Read with =common.org=. Paths are relative to the root of the repo under review.

* Scope

Container image definitions in any repo: production build / runtime Dockerfiles (=Dockerfile=,
=*.Dockerfile=) with their adjacent entrypoint scripts (=*-entrypoint.sh=) and =nginx.conf=; dev
images and their entrypoints; legacy Dockerfiles; and tool images such as a CI runner image (see the
tool-image calibration below). Read alongside the pipeline's build / push step (the BuildKit secret
id it passes, the image name format, the =--build-arg= shape, the build context it passes) and the
chart's Service =targetPort= and migration Job. Not pipeline YAML (=pipeline.org=) or chart YAML
(=helm-chart.org=) — surface contract mismatches with them, don't review their shape. Not
=docker-compose.yml=. Not EF migration content — only the bundle bake step and the entrypoint that
runs it.

* Calibration

Fresh vs legacy:

- *Fresh* Dockerfiles — full house style applies. The repo's best-shaped production Dockerfile is
  the bar.
- *Legacy* Dockerfiles — review-with-mercy: a legacy file is graded against its own file's style,
  not against the fresh shape. Do not flag the absence of a =# syntax= directive, a BuildKit secret
  mount, a cache mount, package-feed auth, a numeric =USER=, or restore-before-source-COPY
  discipline as Bug or Smell. DK-006, DK-007, DK-014, DK-023 and the feed-auth rules do not fire on
  a legacy file. Flag only fresh additions inside a legacy file (a new step introducing a smell
  against the file's own style) or substantive structural edits. Surface the legacy subtree's
  modernization opportunity once at the top if pervasive (CM-005), then move on. Writers don't
  retrofit the fresh shape onto legacy files without an explicit modernization cycle.
- *Mixing fresh and legacy in one file* (a new step in a legacy file that uses BuildKit secret
  syntax while the rest doesn't) → Smell.
- *Targeted CVE / version bumps to legacy files* that follow the file's existing style for minimum
  diff → not a finding.
- When in doubt whether a file is fresh or legacy, ask before reviewing.
- *A tool image* (for example a CI runner image that installs the binaries the runner host needs —
  =kubectl=, =helm=, =jq=, =curl= and the like) is not a service image. No app is built on it, so
  most of this file's rules have no subject there, and three would misfire on correct code. Review
  it for base-image pinning, credential hygiene, and install discipline; nothing else.
  - *Would misfire — not findings there.* DK-026 (production images are multi-stage): a tool image
    has nothing to separate, and single-stage is correct. DK-021 (no dev tooling in a production
    stage): the tooling /is/ the deliverable. DK-015 (no =USER root= in a production runtime
    stage): =USER root= mid-file for the package installs, with the file ending on a non-root
    =USER=, is the intended shape — flag a =USER root= that is never dropped, not this shape.
  - *No subject.* The whole package-feed / restore / publish family (DK-002 through DK-011) and
    DK-027 — no feed, no restore, no =/publish=. DK-017 / DK-018 — no =EXPOSE=, no chart Service.
    DK-034 / DK-042 — not an nginx base. DK-029 — not a dev image. DK-019 / DK-020 are written for
    =apt-get=; on Alpine the equivalent is =apk add --no-cache=, which already satisfies their
    intent — don't flag the absence of apt flags.
  - *Apply normally.* DK-001 (no hardcoded credentials), DK-012 / DK-013 (base tag pinned, no
    =:latest=), DK-014 (ends non-root), DK-023 / DK-024 (if no mounts are used, the absence of a
    =# syntax= directive is correct, not a gap).

*Match the project's established choices.* The base images, Dockerfile layout and naming, =USER=
form, entrypoint permission shape, base-version parameterization, =# syntax= pin, and web-server
runtime-config mechanism a project has established are the ones its Dockerfiles are graded
against. The choices this file names — =docker/dockerfile:1.7= as the =# syntax= pin,
=nginxinc/nginx-unprivileged:*=, the =api.Dockerfile= / =web.Dockerfile= / =migrate.Dockerfile=
split, a numeric =USER= uid:gid, ~--chmod=0755~ on the COPY, ~ARG DOTNET_VERSION~
parameterization, the =/docker-entrypoint.d/= render-config script — are the default only for a
project that has established none. A project has established a choice when its existing
Dockerfiles use it. A fresh Dockerfile that brings in a second shape beside the established one is
the finding; one that follows the established shape rather than this file's default is not. Moving
such a project onto the default is a migration asked for explicitly, never a review finding. A rule
written for one toolchain or cloud — .NET restore and publish, an EF Core migration bundle, Azure
Artifacts feed auth through the NuGet credential provider, an nginx base — has no subject in a
project that does not use it, and its =Applies to= names that toolchain or cloud. DK-003, DK-006,
DK-007, DK-008, DK-009, DK-011, DK-014, DK-021, DK-023, DK-025, DK-027, DK-031, DK-034, DK-036,
DK-039, DK-041, DK-042, DK-043, DK-046, DK-049, DK-052 and DK-055 carry this scoping in their own
fields. It is
separate from the legacy and tool-image calibration above, which stand as written.

Not findings — house style: the lack of =HEALTHCHECK= on an image whose health is owned by
Kubernetes probes (DK-022); an ~ARG DOTNET_VERSION=<version>~ default literal (the pipeline may
accept the default — flagging the literal version is noise); several secret-mount blocks in one
Dockerfile (restore and EF bundle steps both need feed auth); a numeric prefix on a script COPYed
into =/docker-entrypoint.d/= (the nginx base sorts =/docker-entrypoint.d/*.sh= lexically — numeric
prefixes are house style); a dev image's =dotnet tool install --tool-path /usr/local/bin dotnet-ef=
without a version pin (acceptable for dev tooling); a dev image's runtime feed-token injection via
compose =environment:= (the documented dev pattern — a token baked at build is the issue, not the
runtime env var); the =--link= flag's presence or absence in isolation (DK-053).

Confirm pipeline-contract findings (a secret id rename, an =EXPOSE= mismatch, an entrypoint move) by
globbing the pipeline and chart directories for the actual consumer before flagging — a "broken
contract" finding that matches a paired update elsewhere is noise.

Rules lifted from the Dockerfile writer's house conventions with no reviewer rule yet carry Smell
severity unless the entry states otherwise.

* Secrets

** DK-001 — No hardcoded credentials

- *Severity:* Bug
- *Applies to:* all code
- *Rule:* Hardcoded PAT, token, password, API key, or connection string in =ARG=, =ENV=, =RUN=, or
  a baked entrypoint script.
- *Not a finding:* none.
- *Precedent:* none yet

** DK-002 — BuildKit secrets are read from =/run/secrets/<id>=

- *Severity:* Bug
- *Applies to:* all code
- *Rule:* Secret value read from a filesystem location other than =/run/secrets/<id>= when using a
  BuildKit secret mount — the mount path is determined by =id=.
- *Not a finding:* none.
- *Precedent:* none yet

** DK-003 — The BuildKit secret id matches what the pipeline passes

- *Severity:* Bug
- *Applies to:* all production Dockerfiles that take a BuildKit secret from the pipeline; the
  credential-provider shape, only those restoring NuGet packages from an authenticated feed
- *Rule:* BuildKit secret =id= renamed on a production Dockerfile without the matching pipeline
  change. The pipeline passes the secret by id (for example
  ~--secret id=feed_token,env=FEED_ACCESSTOKEN~); a rename breaks the build silently on the next
  pipeline run. Use ~--mount=type=secret,id=<id>,required=true~ on every step that needs
  package-feed credential-provider auth, with the feed-endpoints variable (for Azure Artifacts,
  =VSS_NUGET_EXTERNAL_FEED_ENDPOINTS=) inlined reading from =/run/secrets/<id>=. A rename is a
  paired change with =mz-pipeline-writer= (PL-038 in =pipeline.org=).
- *Not a finding:* more than one mount block for the same id in one Dockerfile (restore and EF
  bundle steps both need it). The credential-provider shape in a project that restores no NuGet
  packages from an authenticated feed — no subject (Calibration).
- *Precedent:* none yet

** DK-004 — A feed token is never baked at build time

- *Severity:* Bug
- *Applies to:* all code
- *Rule:* A package-feed token (for example =FEED_ACCESSTOKEN=) baked via =ARG= or =ENV= at build
  time — the PAT lands in image layers and =docker history=. Production uses the BuildKit secret;
  dev uses runtime env.
- *Not a finding:* a dev image reading the token from container env at start (compose
  =environment:=).
- *Precedent:* none yet

** DK-005 — Dev images use runtime env injection, not BuildKit secrets

- *Severity:* Smell
- *Applies to:* dev images
- *Rule:* Dev image using a BuildKit secret instead of runtime env injection. The dev pattern is
  compose =environment:= supplying the feed token at start.
- *Not a finding:* none.
- *Precedent:* none yet

* Layer and cache hygiene

** DK-006 — Restore before =COPY . .=

- *Severity:* Bug
- *Applies to:* fresh Dockerfiles that restore .NET (=dotnet restore=) or npm (=npm ci=)
  dependencies
- *Rule:* =COPY . .= before =dotnet restore= — invalidates the restore cache on every source change.
  COPY =.csproj=, =Directory.Packages.props=, =global.json=, =NuGet.Config=, =*.sln= first;
  =dotnet restore=; then =COPY . .=. Same shape for npm: =package.json= + =package-lock.json=
  first, =npm ci=, then =COPY . .=.
- *Not a finding:* a legacy single-stage restore-then-source COPY (see Calibration). A Dockerfile
  that restores neither .NET nor npm dependencies — no subject (Calibration).
- *Precedent:* none yet

** DK-007 — Restore, build, and publish use the package cache mount

- *Severity:* Smell
- *Applies to:* fresh production Dockerfiles that restore .NET or npm dependencies
- *Rule:* Restore step missing ~--mount=type=cache,target=/root/.nuget/packages~ (on every restore,
  build, and publish step in the build stage). Same for npm: missing
  ~--mount=type=cache,target=/root/.npm~.
- *Not a finding:* legacy files. A Dockerfile that restores neither .NET nor npm dependencies — no
  subject (Calibration).
- *Precedent:* none yet

** DK-008 — Build steps don't re-run restore

- *Severity:* Smell
- *Applies to:* Dockerfiles that build .NET projects
- *Rule:* Build / publish steps re-running =dotnet restore= instead of =--no-restore=.
- *Not a finding:* a Dockerfile that builds no .NET project — no subject (Calibration).
- *Precedent:* none yet

** DK-009 — =dotnet publish= is =--no-restore= after an explicit restore

- *Severity:* Smell
- *Applies to:* Dockerfiles that build .NET projects
- *Rule:* =dotnet publish= missing =--no-restore= after an explicit restore step.
- *Not a finding:* a Dockerfile that builds no .NET project — no subject (Calibration).
- *Precedent:* none yet

** DK-010 — Only restore inputs in the restore-cache COPY layer

- *Severity:* Smell
- *Applies to:* all code
- *Rule:* Unrelated files in the restore-cache COPY layer (README, test fixtures, source code) —

** DK-011 — Targeted =.csproj= COPY

* BuildKit features

** DK-023 — A =# syntax= directive whenever mounts are used, =docker/dockerfile:1.7= by default

- *Severity:* Bug
- *Applies to:* all code
- *Rule:* =# syntax= directive missing from a Dockerfile that uses ~--mount=type=secret~ or
  ~--mount=type=cache~. The directive pins the Dockerfile frontend version, so the file builds the
  same on every builder rather than on whichever frontend a builder ships with, and it supplies the
  mount syntax on a builder whose built-in frontend lacks it. A recent builder accepts and builds
  =--mount= without the directive; that an older builder rejects the file without it is not
  verified here. The directive carries the pin the project's existing Dockerfiles use; in a project
  that has established none, it is ~# syntax=docker/dockerfile:1.7~ and is required on every
  production Dockerfile.
- *Not a finding:* legacy files (no BuildKit features). A =# syntax= pin other than =1.7= that the
  project's existing Dockerfiles use — matching the project, not drift (Calibration; DK-025 grades
  the pin's age). The directive under CM-003 — a parser directive is not a comment (DK-056).
- *Precedent:* none yet

** DK-024 — No unused =# syntax= directive

- *Severity:* Suggestion
- *Applies to:* all code
- *Rule:* ~# syntax=docker/dockerfile:1.7~ present but no BuildKit features used. Drop it or use
  the features.
- *Not a finding:* none.
- *Precedent:* none yet

** DK-025 — =# syntax= pinned no older than the project's pin, =1.7= by default

- *Severity:* Smell
- *Applies to:* new Dockerfiles

  existing Dockerfiles use, or, in a project that has established none, older than =1.7=.
- *Not a finding:* a new Dockerfile carrying the pin the project's existing Dockerfiles use —

- *Not a finding:* none.

** DK-029 — Dev images stay single-stage

* Entrypoint discipline

** DK-030 — Exec-form =ENTRYPOINT= and =CMD=

- *Severity:* Smell
- *Applies to:* all code
- *Rule:* Shell-form =ENTRYPOINT= or =CMD= (=ENTRYPOINT dotnet App.dll=) — wraps in =/bin/sh -c=,
  breaks signal handling. Use =["dotnet", "App.dll"]=.
- *Not a finding:* none.
- *Precedent:* none yet

** DK-031 — Entrypoint scripts are executable, ~--chmod=0755~ on the COPY by default

- *Severity:* Bug
- *Applies to:* all code
- *Rule:* Entrypoint script COPYed without ~--chmod=0755~ and no subsequent =RUN chmod +x= — won't
  execute. The shape is the one the project's existing Dockerfiles use; in a project that has
  established none, it is ~--chmod=0755~ on the COPY, no separate =chmod= step.
- *Not a finding:* a separate =RUN chmod +x= step in a project whose existing Dockerfiles use that
  form — matching the project, not drift (Calibration).
- *Precedent:* none yet

** DK-032 — Entrypoint scripts live beside their Dockerfile

** DK-034 — nginx runtime config renders from =/docker-entrypoint.d/=

- *Severity:* Smell

- *Not a finding:* a numeric prefix on the render-config script (for example =40-=) — house style. A

** DK-036 — A build =ARG= stays while the pipeline passes it

- *Severity:* Bug
- *Applies to:* all code
- *Rule:* An =ARG= removed while the pipeline passes it as ~--build-arg <name>=...~ (check the

  build still succeeds, and nothing reports it. =ARG DOTNET_VERSION= with
  ~--build-arg DOTNET_VERSION=...~ is an example only; the rule holds for any build =ARG= in any
  toolchain.
- *Not a finding:* the =ARG='s default literal.
- *Precedent:* none yet

** DK-044 — =EXPOSE 8080= on =nginx-unprivileged:*=

** DK-056 — CM-003 in Dockerfiles and their entrypoint scripts, directives excepted

- *Severity:* Smell
- *Applies to:* new or touched code only, in Dockerfiles and the entrypoint scripts they COPY
- *Rule:* CM-003 applies — an explanatory =#= line in a Dockerfile, and an explanatory =#= line in
  an entrypoint script it COPYs (=*-entrypoint.sh=, a script under =/docker-entrypoint.d/=), are
  both comments here. Name the stage, the script, or the variable so the step reads without one,
  with design rationale moved to the pull-request description or the issue.
- *Not a finding:* one carve-out, and no other. A directive is not a comment for this rule: a
  Dockerfile parser directive (~# syntax=...~, ~# escape=...~, ~# check=...~), or a tool directive
  such as ~# hadolint ignore=...~ in a Dockerfile or ~# shellcheck disable=...~ in an entrypoint
  script, or an entrypoint script's first-line interpreter directive (=#!/bin/sh=,
  =#!/usr/bin/env bash=). Whether the warning a tool directive suppresses was justified is graded
  on its own, not under CM-003. The =# syntax= directive itself is graded by DK-023, DK-024 and
  DK-025.
- *Precedent:* none yet

- *Severity:* Smell

  multi-stage image in a project whose existing Dockerfiles use that form — matching the project,
  not drift (Calibration).
