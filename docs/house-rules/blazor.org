#+title: Blazor house rules (BZ)

Read with =csharp.org= and =common.org=. These are deltas on top of both. A BZ entry whose title
names a CS id is a delta: the parent rule applies as written, and the entry records only what
differs for Blazor. Paths are relative to the Blazor project root unless stated.

* Scope

Blazor WebAssembly projects in any repo: =.razor= pages and components, =_Imports.razor=,
=App.razor=, =Program.cs=, supporting C# under =Services/=, =Clients/= and =Theme/=, and the
project stylesheets under =wwwroot/css/=, plus their paired test projects for structure and
coverage. Not a shared plain-.NET contracts library the Blazor project references (that is
=csharp.org=). Not the API, charts, Dockerfiles, or pipelines.

* Calibration

- Uniform severity unless the repo contract names a legacy Blazor area. Calibrate against the
  repo's established Blazor project. Where a repo has more than one, prefer the parallel file of
  the same shape in the project under review as the baseline, and fall back to the established
  project's file. Auth wiring is the usual exception to one-for-one transfer — one project may use
  an OIDC provider directly and another MSAL — so calibrate each project's =Program.cs= auth
  registration against its own auth pattern. When no project establishes a policy, apply standard
  Blazor / MudBlazor practice.
- Cross-cutting .NET rules (file-scoped namespaces, =_camelCase= fields, =I=-prefixed interfaces,
  primary constructors for DI, =using= order, disposal of =IDisposable=) are *stated* in
  =csharp.org= and *applied here by =mz-blazor-reviewer=*. Where no other reviewer runs on these
  paths, a =csharp.org= rule with no BZ entry is this reviewer's to raise, citing the CS id. "Flag
  here only when the smell is Blazor-specific" governs where a *new rule is written*, not which
  rules are enforced: a BZ entry exists only where Blazor changes the parent (BZ-038 on CS-011,
  BZ-052 on CM-003), and its absence means the parent applies unmodified — never that the parent
  is out of scope. Applying a parent rule here is still bounded by that rule's own conditions
  (its touched-unit clause, its carve-outs): widening which reviewer applies a rule does not widen
  what the rule reaches, and a parent rule over a mixed baseline is not turned into a finding
  against the established half of it.
- A minimal =Theme/= folder is not a finding when the project does not customize MudBlazor's
  theme.
- bUnit-stack test conventions (=TestContext=, =JSRuntimeMode.Loose=, =TestHost= wrapper shape,
  NSubstitute vs Moq, =Assert.*= vs Shouldly) live in the Test style group below
  (BZ-065..BZ-076); cite those ids rather than deferring. It is NSubstitute + =Assert.*=, full
  stop — the documented Blazor exception to the .NET Moq + Shouldly default (BZ-065).
- Canonical references — a page component, a reusable component, a stateful service, a JSInterop
  wrapper, a typed client, and the =Program.cs= bootstrap — are the repo's own. Where the repo
  contract names them, calibrate against those; a canonical file that itself carries drift under
  another rule (a separate-file interface under CS-017, for instance) is not part of the shape to
  copy.
- Rules lifted from =mz-blazor-writer= house conventions with no reviewer rule yet carry Smell
  severity unless the entry states otherwise.

* Razor file shape

** BZ-002 — Directive order =@namespace= → =@page= → =@attribute= → =@using= → =@inject= → =@implements=

- *Severity:* Smell
- *Applies to:* all =.razor= files
- *Rule:* Directive order other than =@namespace= (omit for =Pages/=) → =@page= (pages only) →
  =@attribute= (=[Authorize]= and the like) → =@using= (per-file imports, one contiguous block;
  BZ-077 orders inside it) → =@inject= (one per dependency) → =@implements=. Markup, then
  =@code { }= at the bottom.
- *Not a finding:* a directive the file has no need of — most components carry no =@page=,
  =@attribute=, or =@using= at all, and the order constrains relative position rather than
  presence. Whether a given =@using= belongs in the file at all is BZ-007's question, not this
  rule's.
- *Precedent:* none yet

** BZ-081 — A declared style rule has a consumer

- *Severity:* Smell
- *Applies to:* new or touched code only
- *Rule:* A selector in a project stylesheet (=wwwroot/css/=) that no markup in the project can
  match. This is live dead code, and nothing else in the registry or the toolchain catches it:
  CM-002 reaches markup that was *commented out*, not a rule left declared and unreachable; the
  build does not fail, no test renders it, and a later reader cannot tell a selector waiting for
  its markup from one whose markup is gone. Establish it by searching the project for the class or
  id name across =.razor=, =.razor.css=, =.html= and any C# that composes a class list — a class
  can be assembled from a string, so markup grep alone is not the test. Delete the rule; git is
  the history. A rule kept deliberately for markup that is about to land is restored with that
  markup, not left ahead of it.
- *Not a finding:* a selector matched by markup *MudBlazor* renders rather than the project —
  =.mud-*= overrides, =aria-*= and =[data-*]= attribute selectors, element and reset selectors —
  none of which the search above will find in project markup. A custom property or token consumed
  by another rule in the same sheet. A selector whose class is composed in C# and therefore found
  by the C# half of the search. Pre-existing unreachable rules in a stylesheet the change does not
  touch — drift, surfaced once per CM-005 and filed.
- *Precedent:* none yet

** BZ-084 — Helper text in a value cell is an element inside the =<dd>=, carrying the project's helper-text class

- *Severity:* Smell
- *Applies to:* new or touched code only
- *Rule:* Helper text qualifying a rendered value in a definition list — "Data unavailable" after
  the "—" a display helper returns — is an element placed inside the =<dd>= that holds the value,
  carrying the class the project already uses for helper text. Not a sibling of the =<dd>=, not a
  new class. The rule fixes the class and the containment, not the element: a =<div>= carrying a
  class that sets only font size and colour renders on its own line under the value, and that is
  acceptable.
- *Not a finding:* helper text under a form input — outside this rule, which covers
  definition-list value cells only. A =<dd>= carrying no helper text. Pre-existing helper text in
  untouched markup — drift, surfaced once per CM-005.
- *Precedent:* none yet

*Open question — whether a value rendered outside a labelled column owes a visible label.* A
value shown bare on a detail surface (a card head showing a status word, say) where a list
surface gives the same value a column header is a stance question, not a defect class: "every
rendered value carries a visible label" reaches far more markup than any one instance, and
whether a nearby heading, column, or card title already labels each bare value has to be read
case by case. This is not an accessibility question and BZ-079 does not reach it: that rule
grades an /interactive/ element whose accessible name disagrees with its visible one, and a
=<span>= carrying a word is neither interactive nor misnamed — a screen reader reads exactly what
a sighted user sees. BZ-030 / BZ-031 / BZ-032 are interactive-element rules for the same reason.
*Until the question is decided, an unlabelled rendered value is not a finding under any rule.*

** BZ-079 — The accessible name contains the visible label

- *Severity:* Bug
- *Applies to:* all code
- *Rule:* An interactive element whose =aria-label= — or whose =aria-labelledby= target — does not
  contain the element's own visible label text. The accessible name *replaces* the visible one for
  assistive technology and is also the string speech-recognition software matches, so a user who
  says the words they can see activates nothing: this is the WCAG 2.5.3 Label in Name failure.
  BZ-030, BZ-031 and BZ-032 grade whether an accessible name is *present*; this rule grades whether
  it *agrees* with what the user can see, and an element can satisfy all three of those and still
  be this finding. Build the label around the visible text rather than beside it — start the
  accessible name with the rendered string and append the extra context, rather than substituting
  a different noun for it. Where the visible text comes from a display helper rather than a
  literal, read the helper: the markup shows a call, and the string the label has to contain is
  whatever that call can return.
- *Not a finding:* an =aria-label= that *extends* the visible label with extra words, which is the
  shape this rule asks for. An icon-only control with no visible text (BZ-032's subject). An
  =aria-hidden= or decorative element. A visible label that is itself an icon or a glyph with no
  reading.
- *Precedent:* the remedy, generically — compute the visible string once into a local from the
  display helper, render that local as the link text, and build the name around it:
  ~aria-label="@($"{recordName} record #{record.Number}")"~. The defect it replaces: a label built
  from a raw field (=record.Name=) while the visible text came from a helper that falls back to
  "Application #<n>" when the name is blank — so the name read "record #801" where the link read
  "Application #801", omitting the one word a voice user would say.

** BZ-080 — One announcement per load outcome, and never two attributes that disagree

- *Severity:* Smell
- *Applies to:* new or touched code only
- *Rule:* Two shapes, both about how a page tells a screen-reader user that a load failed or
  finished. *(a) ~role="alert"~ and an explicit =aria-live= on the same element.* ~role="alert"~
  already implies ~aria-live="assertive"~; the explicit attribute wins, so the element reads as one
  statement and behaves as the other — an error marked ~aria-live="polite"~ is queued behind
  whatever is currently speaking instead of interrupting, which is the opposite of what the author
  wrote ~role="alert"~ to get. Carry one or the other: ~role="alert"~ alone for a message that
  must interrupt, or =aria-live= alone on a region that is not an alert. *(b) A new mechanism.* A
  page announcing the same kind of outcome by a mechanism none of the project's existing pages
  uses, when the project already has one or more — it does not need another until someone picks
  between them (see the open question below this group). Match one already on disk and say which
  in the cycle report.
- *Not a finding:* either established mechanism on its own — a conditionally-rendered alert
  carrying ~role="alert"~ and no =aria-live=, or a permanently-present =sr-only= region carrying
  =aria-live= and no ~role="alert"~. Which of the project's existing mechanisms a page picks, until
  the open question is settled. =aria-live= on a region that is genuinely not an alert — a status
  line, a result count — alongside a separate alert element. An existing contradictory pair in
  markup the change does not touch — drift, surfaced once per CM-005 and filed.
- *Precedent:* shape (a)'s defect — a =MudAlert= carrying both ~role="alert"~ and
  ~aria-live="polite"~. Its remedy — the same conditionally-rendered =MudAlert= carrying
  ~role="alert"~ and no =aria-live=, pinned by a test asserting the element has no politeness
  attribute at all.

*Open question — which announcement mechanism is the house shape.* Two are in common use: a
conditionally-rendered =MudAlert= with ~role="alert"~, announced when the node is inserted, and a
permanently-present =sr-only= =aria-live= region whose text changes. The second is the more
defensive — a live region that exists before its content arrives is honoured by more assistive
technology than a node inserted with ~role="alert"~ — and the first is less markup and keeps the
message in one place. Until a repo picks one, BZ-080 grades only the contradictory-attribute shape
and the introduction of a mechanism the project does not already use; a page using an existing one
is not a finding.

** BZ-082 — A response is discarded when the parameter that requested it has changed

- *Severity:* Bug
- *Applies to:* new or touched code only
- *Rule:* An =OnParametersSetAsync=, =OnInitializedAsync=, or event handler that records the
  parameter it is loading for, awaits a call, and then assigns the result to component state
  *without re-reading that parameter after the await*. Blazor does not serialise the lifecycle
  against navigation: navigating A → B before A's response lands leaves two calls in flight
  against one component instance, and the slower one wins the assignment — so the page renders A's
  record under B's route, with no exception, no error state, and nothing in the logs. Re-read the
  parameter after *each* await and discard a result that no longer matches
  (~if (_loadedId != Id) { return; }~ after the await, not only the guard before the call). That
  discard is the whole of this rule's remedy. *Cancelling the abandoned request is a separate
  question and deliberately not required here* — see the open question below this group; a page
  that re-reads the parameter and discards correctly satisfies this rule whether or not it passes
  a token, and a reviewer should not read a missing token as a BZ-082 finding. CS-003 / BZ-048
  govern *whether a token is passed by a method that declares one*; this rule governs *what
  happens to a result that arrives anyway*, and a page can satisfy both of those and still be this
  finding — a token cancelled on navigation does not retract a response already on the wire.
- *Not a finding:* a load with no parameter that can go stale — =OnInitializedAsync= on a
  parameterless page, which runs once per component instance. A route change that disposes the
  component rather than re-parameterising it, where the stale assignment has no component left to
  reach. A result assigned to a local the render never reads. A guard before the call that is the
  whole of the load (a cached value returned synchronously, no await between the read and the
  assignment).
- *Precedent:* the remedy, generically — hold the response in locals across the await and commit
  them in a =finally= guarded by ~var requestedIdIsStillTheOneOnTheRoute = _loadedId == requestedId;~,
  re-reading the field a second =OnParametersSetAsync= would have overwritten; pinned by a test
  that holds both responses on =TaskCompletionSource= and completes them out of order. The defect
  it replaces: setting ~_loadedId = Id~ /before/ the await and assigning the results after it with
  no re-check.

*Open question — whether a page owes a =CancellationTokenSource= so a lifecycle override has a
token to pass.* CS-003 and BZ-048 grade a =Task=-returning method the author *declares* that
accepts no =CancellationToken=. A Blazor lifecycle override — =OnInitializedAsync=,
=OnParametersSetAsync=, =OnAfterRenderAsync= — has a signature the framework fixes and cannot
declare one, so neither rule reaches a client call made from inside it where the client accepts a
token and none is passed. Passing one means the component owning a =CancellationTokenSource=,
cancelling it on parameter change and disposing it — which drags in =IDisposable= on a page that
otherwise needs none, and interacts with BZ-003 / BZ-011 / BZ-019. *What the absence costs is
settled and is not a correctness defect:* one abandoned in-flight GET per navigation, whose
response the BZ-082 staleness guard already discards, so nothing wrong renders and nothing is
logged — the cost is a wasted request and a wasted deserialization. Whether that is worth a
disposable token source on every parameterised page is a design call per repo. *Until it is
decided, a client call made from a lifecycle override with no token is not a finding under any
rule*, and in particular not under BZ-082. This is distinct from the Test style group's
=CancellationToken=-reach question, which is about a typed-client *test* asserting the token
reaches the stub handler; neither question reaches or defers the other.

** BZ-059 — CS-014 in =@code= blocks and =Services/= / =Clients/=

  value handed in makes it a total function of its arguments; and three-or-more-way branching on a

** BZ-063 — Typed client returns raw responses or unwraps the payload wrapper, never both

- *Severity:* Smell
- *Applies to:* new or touched code only
- *Rule:* =record= types for ={ "<entity>Id": "..." }= payload wrappers rather than poking at a
  =JsonDocument=. A typed client is uniform in what it hands its callers: either every method
  returns a raw =HttpResponseMessage= / the wrapper type and the caller unwraps, or every method
  unwraps inside the client and returns the domain type. A client that does both forces each
  caller to learn which convention each method follows. For this test a =Task<ApiResponse<T>>=
  return *does* count as returning the wrapper type: the caller receives the envelope and reads
  =Data= off it, which is precisely the mixed convention named above. The carve-out below is what
  makes a split acceptable; it is not a claim that such a client is uniform. This rule's "payload
  wrapper" is the ={ "<entity>Id": ... }= id wrapper; an =ApiResponse<T>=-style protocol envelope
  is a different thing, and the two are not to be read as one.
- *Not a finding:* methods that differ in the *wire shape they read* while returning the same kind
  of thing. A client whose methods all return unwrapped domain types is uniform for this rule
  whether a given body arrived as a bare DTO or inside an =ApiResponse<T>= protocol envelope — the
  protocol is the client's own business and is invisible at the interface. *A client
  mid-conversion to the envelope* — a condition checked against the endpoints the client calls,
  not against a list of files. The split is exempt when the API behind the client is itself
  part-converted, some of its endpoints emitting an =ApiResponse<T>= envelope and the rest bare
  DTOs, and the client's return types track that split method for method: each method returns the
  envelope exactly when its own endpoint emits one, and returns the domain type exactly when its
  own endpoint emits a bare DTO. In that state the client cannot be made uniform from its own side
  — giving an unconverted method an envelope return would mean synthesising =IsSuccess= and
  =StatusCode= at the call site, which =csharp.org= CS-091 forbids outright, the envelope's status
  being the operation's own outcome, chosen by the producer, never derived from the transport or
  invented downstream. So the split is not drift: it is the client faithfully reporting an API
  that is half-converted, and it resolves when the producer side does. A split that does *not*
  track the endpoints is this rule's finding and the exemption does not reach it — an envelope
  return invented over a bare-DTO endpoint, or two conventions spread across endpoints that emit
  the same shape. Once the producer side converts and the endpoints emit envelopes uniformly, the
  remedy is available and the split is a finding again. The finding is a mixed *return*
  convention, never a mixed protocol. *What this exemption leaves open, and what a consumer of
  such a client has to know:* the two conventions differ in *failure behaviour*, not only in
  return type — and they differ in one specific way rather than in general. An unconverted method
  calls =EnsureSuccessStatusCode()= and throws on any failed call. The enveloped method does not
  throw on an *operation* failure: a response the API itself meant as a failure comes back
  normally, with =IsSuccess: false=, =Data= possibly populated, and =Messages= carrying what the
  user is meant to be told. It throws on everything else, and that is more than one case. The call
  itself throws before any body exists — the =HttpClient= call ahead of the parser raises
  =HttpRequestException= on a transport failure exactly as an unconverted method's call does — and
  the parser behind it throws a protocol exception from three sites, named by condition in CS-092:
  the body is not JSON; the body is JSON carrying no =isSuccess= marker; and the marker *is*
  present while the payload does not bind to =T=. That last one is an envelope-shaped body, so an
  enveloped method is not safe to call without =try=/=catch=. What the =try=/=catch= cannot do is
  stand in for branching on =IsSuccess=. A caller that treats it as sufficient — as it is for an
  unconverted method — and reads =Data= without branching, renders a failed operation as a success
  with empty data and silently drops the messages the API deliberately sent. Branching on
  =IsSuccess= is CS-091 and it is not optional on these methods.
- *Precedent:* private =record= id wrappers (=OrderIdEnvelope=, =NoteIdEnvelope=) each
  unwrapped inside the client, so a =CreateOrder= method returns =Guid=, not the wrapper.

** BZ-078 — A typed-client test arranges a body the server can send, and never pins an expectation to an enum's zero member

- *Severity:* Smell
- *Applies to:* new or touched typed-client tests in the Blazor test projects, and the tests of a
  *wire-format collaborator* those clients read through (an enveloped-response parser), to the
  extent of the payload clause in the Rule
- *Rule:* A stub-handler response body the real API cannot emit, or an expectation pinned to an
  enum's zero member where that member is a real business value. The two halves arrive as one
  defect and are stated as one rule because the second is what hides the first: a body that omits
  a non-nullable enum property the API always writes — an API that omits nulls and nothing else —
  paired with an assertion that the deserialized value was the enum's ~= 0~ member, where that
  member means a real value (say, "serviced by vendor A") rather than "unknown". "Field absent" and
  the zero-member value are then indistinguishable, and the test records the indistinguishable case
  as intended behavior. Arrange only bodies the server actually sends. The authority ranking,
  strongest first: a response *captured* from the running API; a body *transcribed
  property-by-property from an integration test that asserts the serialized response* of the same
  endpoint, which ranks with a capture because that test pins the wire shape and, unlike a
  capture, breaks again when the shape moves — a transcription names the test it came from — in
  the fixture's own name, or once in a type that groups the fixtures sharing that source, which is
  the better shape as soon as more than one body comes from one test because it states the
  authority once and survives additions — and neither that name nor the test's name may claim a
  capture that did not happen, since the name is the only record a later reader has of where the
  body's authority came from; an *omission the API genuinely makes* (a null figure under its
  ignore-nulls posture). Below all three, and this rule's subject, is a body composed from the
  DTO's property list, from an OpenAPI document, or from the writer's memory of the shape. Where an
  enum property is in play, assert a non-zero member, or assert the zero member only from a body
  that carries it explicitly. CS-072 / BZ-075 ask for null and empty coverage; this rule asks
  whether the arranged body is producible at all, which they do not. *A wire-format collaborator's
  own test is reached only on the payload half.* A parser generic over =T= is legitimately
  exercised with bodies no endpoint can send — a non-envelope body, a plain-text body, an empty or
  =null= body — because the unproducible body /is/ the subject there; those sit under
  =Not a finding= and this rule does not touch them. Where such a test asserts *payload field
  values*, the payload JSON owes the same authority a typed-client fixture owes. A narrower =T=
  than any endpoint returns is acceptable, the collaborator being generic and the endpoint's
  payload type not its subject, *provided the payload JSON is itself transcribed from a real body*
  — for example a nested DTO that reaches the wire only under a parent property, transcribed from
  the parent's real body.
- *Not a finding:* a deliberately malformed, truncated, or empty body in a test whose subject *is*
  the client's error handling, where the name and the assertion say so. A body omitting a property
  the API genuinely omits. An enum whose zero member is a real =Unknown= / =Unspecified= sentinel,
  where asserting it from an absent field is the intended coverage.
- *Precedent:* the corrected shape — transcribed bodies grouped in a nested type whose name
  records their source once for the whole family (=<IntegrationTestName>Transcriptions=), each
  test asserting a non-zero enum member from a body that carries the property explicitly. Where
  the tier stops — a ProblemDetails body whose integration test pins only =status= and =title=
  stays outside the grouping type, because its =type= URI and =traceId= are pinned nowhere and
  grouping it would claim a transcription's authority over the half that has none.

** BZ-083 — A log assertion reads the real =ILogger.Log= member off a substitute registered closed over the type under test

- *Severity:* Smell
- *Applies to:* new or touched test code in the Blazor test projects
- *Rule:* A test that needs to prove something was logged, arranged either of the two ways that do
  not work. *(a) Substituting =ILogger<T>= and asserting on =LogError= / =LogWarning= /
  =LogInformation=.* NSubstitute intercepts interface members, and those are not members — they are
  extension methods on =ILogger= over the single =Log<TState>(...)= member, so the assertion is
  really a claim about a framework-internal =TState= instance and its equality, not about the
  message the test means to pin. *(b) Registering a recorder for the open generic =ILogger<>=*
  (=Services.AddSingleton(typeof(ILogger<>), typeof(RecordingLogger<>))=), which replaces *every*
  logger the container resolves rather than the one under test, so the assertion list also
  collects whatever MudBlazor services, the auth plumbing, and any child component logged. The
  shape: substitute =ILogger<T>= *closed* over the component or service under test, register that
  instance (=Services.AddSingleton(_logger);=), and read =_logger.ReceivedCalls()= filtered to the
  real interface member — ~call.GetMethodInfo().Name == nameof(ILogger.Log)~. Shape (a)'s
  extension call does reach the substitute, so the call *is* recorded; what (a) gets wrong is
  asserting through the extension, and =ReceivedCalls()= is how NSubstitute reaches the member
  underneath it. Take off =call.GetArguments()= whatever the fact needs: the level at index 0, the
  formatted message off the state object at index 2, whose =ToString()= is what =ILogger='s own
  default formatter returns, so reading it and calling =formatter(state, exception)= yield the same
  string for a message-with-exception call. Filter on the member name alone when the fact is that
  the failure path logs *at all*; filter on the level and read the message when the fact is about a
  particular line. A test that needs a logger only so the component can resolve one keeps the same
  closed substitute and asserts nothing against it.
- *Not a finding:* =Substitute.For<ILogger<T>>()= in a test that never asserts on it. A
  member-name-only =ReceivedCalls()= filter in a fact whose subject is that something was logged —
  a fact that pins a /particular/ message and filters on nothing but the member name is the
  under-assertion CS-084 grades, not this rule's finding. An open-generic registration in a test
  whose subject genuinely *is* every logger in the render tree, where the test name says so. A
  hand-written =ILogger<T>= recorder, registered closed over the type under test the same way,
  where a substitute genuinely cannot express the assertion — an =EventId=, or a formatter call
  over a state type that is not =FormattedLogValues=; it is the registration this rule grades,
  never the recorder as such.
- *Precedent:* the shape — a =LoggedErrorMessages()= helper filtering =_logger.ReceivedCalls()= to
  =nameof(ILogger.Log)=, then to =LogLevel.Error= at argument 0, and selecting argument 2's
  =ToString()=; the substitute is the class's =_logger= field, closed over the page under test and
  registered with =Services.AddSingleton(_logger);= in the constructor. The member-name-only form
  it extends: =Failed_<x>_load_logs_the_exception_and_shows_error_state=-style facts.
