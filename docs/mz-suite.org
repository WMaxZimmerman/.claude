#+title: mz suite — the contract
#+startup: content

This is the contract every =mz-= agent reads first, and the main agent reads before it hands
work to one. =~/.claude/CLAUDE.md= points here; nothing else loads it.

* What the suite is for

The =mz-= agents are personal fallbacks. They exist for a repo or space that is not yet set up
for agentic work — no =AGENTS.md=, no agents of its own, no plugin enabled. When a session also
has an agent from an enabled plugin, or from the repo's own =.claude/agents/=, that does the same
job, that agent is used instead (the precedence rule in =~/.claude/CLAUDE.md=). The suite is
self-contained when it is called, and steps aside when a repo has its own setup.

* Reading order

Every =mz-= agent, on every run:

1. Reads this file from disk with the =Read= tool. Never from a copy already in hand.
2. Reads the repo's =AGENTS.md= at the repo root. If there is none, reads the repo's root
   =CLAUDE.md=. If there is neither, works from this file and its own built-in defaults.
   Each file the one it reads imports by a line that is =@<path>= alone is part of it.
3. Says once in its report which of the three it used: =Repo contract: AGENTS.md= /
   =Repo contract: CLAUDE.md= / =Repo contract: none — built-in defaults=.

A repo's =AGENTS.md= or =CLAUDE.md= may set rules, and where it conflicts with this file it
wins — surface the conflict in the report. This includes a coding rule written in that file
itself. *One exception:* the house-rules registry and attack angles come only from
=~/.claude/docs/house-rules/=. An =mz-= agent never reads a repo's own =docs/house-rules/= folder,
and never reads or writes a repo's own =docs/runbooks/=.

* Where the suite keeps things

All under =~/.claude/=, which is a git repo synced between machines.

| Path                                   | What                                             | Writer                  |
|----------------------------------------+--------------------------------------------------+-------------------------|
| =agents/mz-*.md=                       | agent definitions                                | =mz-agent-builder=      |
| =skills/mz-*/SKILL.md=                 | skills                                           | =mz-skill-builder=      |
| =docs/mz-suite.org=                    | this contract                                    | Max, or the main agent at his direction |
| =docs/house-rules/=                    | the rules-and-angles registry — see below        | =mz-house-rules-manager= |
| =docs/runbooks/=                       | runbooks, each naming the repo or tool it is about | =mz-runbook-manager=  |
| =docs/agents-md-checklist.org=         | what a repo's =AGENTS.md= should provide         | =mz-agent-builder= for the lines that ride with an agent change; otherwise Max |
| =aptitude/<repo-key>.org=              | Max's per-repo familiarity calibration           | =mz-aptitude-scout=     |
| =repo-notes/<repo-key>.org=            | Max's per-repo answers no repo file can hold      | the main agent, at Max's direction |

Agent and skill files are =.md= because Claude Code requires it. Every other file the suite
keeps is =.org=.

=<repo-name>= is the last path segment of the =origin= remote URL with any =.git= removed; with
no =origin=, the name of the directory =git rev-parse --show-toplevel= prints. It names the repo
in the follow-up issue title.

=<repo-key>= names the aptitude file and the repo-notes file: the owner and the repo name joined by =-=, taken from the
last two path segments of the =origin= URL with any =.git= removed, treating =:= as a separator
and skipping a =_git= segment — so =git@github.com:WMaxZimmerman/gtd.git= gives
=WMaxZimmerman-gtd= and =https://dev.azure.com/org/ai_studio/_git/ge-.claude= gives
=ai_studio-ge-.claude=. With no =origin=, it is =<repo-name>= alone. With an =origin=, worktrees
of one repo share one aptitude file; with none, each worktree's directory name is its own key.
Two different repos can still produce one key — the same owner and name on two hosts, a =-= inside an owner or name (=a-b= + =c= and =a= + =b-c= both give =a-b-c=), or two repos
with no =origin= in directories of one name; =mz-aptitude-scout= stops and asks when the file at
the key describes another repo. A repo-notes file opens with the line =- Repo: <origin URL, or the
=git rev-parse --show-toplevel= path with no origin>=, and an entry in it counts only for the repo
that line names. Two origin URLs name the same repo when their host, owner, and name match, whatever
the transport (SSH or HTTPS); two differing paths with no origin are put to Max as a question — same repo or
not — and never decided by the agent; when Max answers "same repo", the main agent adds the second
path to the =- Repo:= line, so the question is not asked again.

Max's GTD workspace, =~/gtd= (=github.com:WMaxZimmerman/gtd=), is the subject of
=mz-gtd-assistant= and outside =~/.claude/=. Its path and its layout are suite facts in that one
agent's file, where AG-005 does not grade them; any other =mz-= agent hands GTD work to
=mz-gtd-assistant= rather than naming the workspace.

** The house-rules registry

=~/.claude/docs/house-rules/= holds:

- =README.org= — the index, regenerated by =mz-house-rules-manager= on every change.
- =common.org= (prefix =CM=) — rules for all code, read by every reviewer and writer.
- =agents.org= (prefix =AG=) — rules for agent and skill files. Read only by =mz-agent-builder=,
  =mz-agent-auditor=, =mz-skill-builder=, and =mz-skill-auditor=.
- One file per stack — =csharp.org=, =blazor.org=, =angular.org=, =python.org=,
  =dockerfile.org=, =helm-chart.org=, =github-actions.org=, =terraform.org= — read by that
  stack's writer and reviewer, each named in the agent's own First step. =pipeline.org= holds the
  Azure Pipelines rules; no =mz-= writer or reviewer applies it. The =mz-= pipeline agents cover GitHub Actions
  only; Azure Pipelines work goes to a plugin agent where the session has one, else to the main
  agent.
- =angles.org= (ids =A-nn=) — the attack angles =mz-devils-advocate= reports against. An angle
  marked =:agent-files:= applies only when the change touches an agent or skill file; on any
  other change it is reported as =Not applicable — no agent or skill file changed=.

*=angles.org= is load-bearing.* =mz-devils-advocate= stops with =Gate: HOLDS — registry missing=
if it is absent, and will not substitute a list of its own.

* Severity ladder

Every finding, and every rule that grades code, carries exactly one of the three below. A
reporting rule — one that governs how findings are emitted, such as =common.org= CM-005 — carries
none.

- *Bug* — an active correctness problem: a false claim, a rule that contradicts another, a
  reference to a path or fact that does not exist, code that does the wrong thing. Blocks the gate.
- *Smell* — a quality or maintainability problem. Blocks the gate the same as a Bug when the
  change wrote it.
- *Suggestion* — style or preference. No gate weight; recorded, optional.

Calibration is apply-to-new: a long-standing instance is drift, surfaced once at the top of a
review, not per file.

* Roster and delegation rule

The roster is every file matching =~/.claude/agents/mz-*.md=. Count it with
=ls ~/.claude/agents/mz-*.md= rather than trusting a number written anywhere.

When the main agent is working through the suite, it does not edit these surfaces directly:

- *Agent files* (=~/.claude/agents/mz-*.md=) → =mz-agent-builder=, gated by =mz-agent-auditor=.
  Never hand-edited; this includes renames and removals. When an agent starts or stops expecting
  a fact from a repo's =AGENTS.md=, the matching line in =docs/agents-md-checklist.org= rides in
  the same diff.
- *Skill files* (=~/.claude/skills/mz-*/=) → =mz-skill-builder=, gated by =mz-skill-auditor=.
  Deleting or moving a skill file is the main agent's, at the builder's stated hand-off. A
  =skills:= line in an agent file stays =mz-agent-builder='s.
- *=docs/house-rules/=* → =mz-house-rules-manager=. An ask that needs history comes with the
  relevant =git diff= and the rename list from =git diff --name-status -M=, handed over by the
  main agent; the manager holds no shell.
- *=docs/runbooks/=* → =mz-runbook-manager=.
- *Code in the repo being worked on* → the stack writer for that path, gated by its paired
  reviewer. The pairing is named in each writer's own file. A path no stack agent covers is
  worked by the main agent directly, unless the repo's contract routes it elsewhere.
  A /Blazor project/ is a project holding =.razor= components, in any Blazor form, that is not a
  test project; the test project paired with it is its /Blazor test project/, named as such. In
  a Blazor project and its Blazor test project, =mz-blazor-reviewer= is the one reviewer for every file, applying the
  =csharp.org= rules with the =blazor.org= deltas. =mz-csharp-reviewer= gives a second opinion
  once per branch, before the =mz-devils-advocate= gate, on the =.cs= files the branch changed in
  Blazor projects; its findings go to the gate like any reviewer's, and one that duplicates an
  =mz-blazor-reviewer= finding is merged with it. When such files change after its last report — a
  fix round, a later commit — it runs again before the next gate, on those files only.
- *Tech debt and follow-ups* → GitHub issues, filed by =mz-gh-issue-writer=; see Tracking.
- *This file and =~/.claude/CLAUDE.md=* → Max, or the main agent at his explicit direction. A
  change to this file is reviewed by =mz-agent-auditor= in change review before it is committed,
  as a change to an agent file is.

Read-only research is fine directly from the main agent. Local-git history beyond the change
boundary — who introduced a line, bracketing a regression, what changed between two refs —
routes to =mz-git-historian=. =mz-devils-advocate= reads the change boundary itself.

GitHub operations route to the three =mz-gh-= agents through the =gh= CLI: reads to
=mz-gh-scout=; issue create and update to =mz-gh-issue-writer=; pull-request create, comment,
review, and link to =mz-gh-pr-operator=.

*=git fetch= is the main agent's alone.* No delegate runs it. A delegate that needs remote refs
uses =git ls-remote=, which writes nothing. This is a role-scoped rule, not a safety fence.

** Who these rules bind

The delegation rule binds the top-level session — the agent Max is talking to. A delegate whose
system prompt is an =mz-= definition is doing its job when it writes its own surface. The safety
fences below bind every agent, main or delegate.

* Source control

- *Integration branch*: the remote's default branch, read at action time —
  =gh repo view --json defaultBranchRef= on GitHub, else
  =git symbolic-ref refs/remotes/origin/HEAD=. Never assumed to be =main=. A repo contract that
  names one wins.
- *Branch and commit naming*: the repo contract's convention if it has one. Otherwise a branch is
  =<issue-number>-kebab-case-slug= when an issue exists, else =kebab-case-slug=; a commit subject
  is a plain imperative sentence, with =(#<issue-number>)= at the end when an issue exists.
- *No AI attribution* in anything an agent composes (see Safety fences).

* Tracking — tech debt and follow-ups

- *Tech debt* — a pre-existing problem the change did not write — is a GitHub issue in the repo
  being worked on, labelled =tech-debt=, filed by =mz-gh-issue-writer=.
- *Follow-ups* — registry gaps, broken citations, observations about an =mz-= agent, per-PR
  house-rule rulings — are collected through the work and filed when the pull request opens (or,
  with no pull request, when the gate clears) as one issue in =WMaxZimmerman/.claude=, titled
  =mz follow-ups from <repo-name> <branch>=, labelled =mz-follow-up=. Nothing collected, no issue.
  Before filing, the agent searches =WMaxZimmerman/.claude= for an open issue with that exact
  title; when one exists (a later gate round of the same branch), the new items go on it as a
  comment instead of a second issue.
- Every issue description uses the six-heading layout in the =mz-issue-template= skill, except
  the follow-up issue, which keeps its own shape (the skill says how it is recognised).
- *Every filing leaves the machine, so each one needs Max's explicit ask.* The agent shows the
  exact =gh= command and waits. Approving the content is not permission to send it.
- *A repo not on GitHub*: there is nowhere to file tech debt. The gate stops and puts each such
  finding to Max, one at a time: he defers it (only he can) or files it himself. Follow-ups still
  go to =WMaxZimmerman/.claude=.

* How a gated writer runs

A writer proposes its change and applies it; its paired reviewer is the gate in place of a human
approval pause. A writer cannot start its reviewer — no writer holds the =Agent= tool — so it
hands back to the main agent, which runs the reviewer with the cycle's =git diff= against the
base and, when files moved, the rename list from =git diff --name-status -M=. Proceed only if the
review returns no Bug and no Smell the change wrote; otherwise the findings go back to the writer.
A fix round is reviewed the same way before it is committed, however small.

Writers with no paired reviewer — =mz-aptitude-scout=, =mz-runbook-manager=,
=mz-house-rules-manager=, =mz-gh-issue-writer=, =mz-gh-pr-operator=, =mz-erd-writer=, =mz-gtd-assistant= — self-verify
against their own conventions.

Two things still stop and wait for Max: the *interview* a builder runs for a new agent or skill,
and a *Needs Max* verdict from any agent.

** Reviewer findings are never dropped

Every reviewer finding — Bug, Smell, Suggestion — is collected by the main agent, and each
report goes to =mz-devils-advocate= whole, never condensed.

* The =mz-devils-advocate= gate

*When it runs*: before a pull request is opened or updated; and, in a repo with no pull request,
before work reaches the integration branch — a local merge into it, or a push to the remote's
integration branch. Pushing or merging any other branch needs no gate. Not before each commit.

Every accumulated finding plus the main agent's disposition of each goes to =mz-devils-advocate=.

- An upheld finding is fixed, in a commit on the branch, before the pull request is opened or
  updated or the work reaches the integration branch.
- The main agent has *no authority to defer* an upheld finding. Only Max can, per finding,
  never as a batch.
- A Bug or Smell the change wrote blocks the gate. A Suggestion carries no weight — except one a
  design consequence rides on, which goes to *Needs Max*.
- A pre-existing Bug or Smell that is small — fixable in files the change already touches, in at
  most one extra cycle, changing nothing others depend on — is fixed. Every other pre-existing
  Bug or Smell is filed as tech debt (see Tracking) before the gate clears.
- =mz-gh-pr-operator= refuses to open or update a pull request without a =Gate: CLEAR= ruling for
  the exact commit it publishes, ruled on a clean working tree, carrying the =### Angles= section.
  A draft toggle on an existing pull request — marking it draft, or marking a draft ready for
  review — is not an update for this rule: it publishes no commit and changes no text, so it needs
  no ruling and no ruling post. The main agent likewise does not merge into or push to the
  integration branch without a =Gate: CLEAR= ruling.
- A suspicion no agent could trace to a path and a reachable trigger is not a finding: it goes
  under =### Could not trace=, with no gate weight, and is never fixed, filed, or put to Max.

* Review scope

- *The wrote-this-line test.* A reviewer flags what the change wrote. A pre-existing problem the
  change exposes is reported as *Pre-existing, file it*. A copy that now differs from its
  siblings is the author's; a false sentence the change wrote is the author's.
- *Trace before raising.* A claim that something will go wrong is a Bug or Smell only after it
  has been traced end to end: the entry point, the path across every boundary, and how the
  triggering state arises. A defect visible on the written line needs no trace.
- *Plain English.* A finding describes the problem in words, never an invented label.
- *Citations.* A durable citation — one that stays in a file — never carries a line number:
  prose by section heading, code by file and symbol. A finding's location in a review keeps
  =file:line=, because it is read at once against the same tree.
- *Comments* in code are governed by =common.org=; in an agent or skill file an HTML comment is a
  Smell.

* Testing and verification

- The repo contract's test and build commands, if it names any. Otherwise the agent finds them
  from the repo (build files, scripts, CI config), says what it found and how, and runs them.
- A repo with no test suite: say so; never claim a suite ran.
- *For a change to an =mz-= agent*: exercise it in a fresh session after the last edit —
  =claude -p= from a directory where the change applies — and report the command and its actual
  output. A session started before the edit does not see it. =mz-devils-advocate= enforces this.
- Report every check as the command and its actual output, never a summary.

* Main-agent routines

- *Aptitude check*, the first time the suite is used in a session: read
  =~/.claude/aptitude/<repo-key>.org= and confirm it covers the current commit-author identity.
  If it is missing or for someone else, invoke =mz-aptitude-scout=. Pitch explanations to it.
- *Plan pass*, on demand before a substantial piece of work: =mz-devils-advocate= attacks the
  plan; its =P-n= challenges carry into the gate. On GitHub, hand it =mz-gh-scout='s search of
  open =tech-debt= issues for the files the plan names; put each pull-in it proposes to Max one at
  a time.
- *Blazor work.* Before =mz-blazor-writer='s first cycle in a project that references no
  UI component library, MudBlazor or another, and whose repo contract records no UI-library decision, hand it
  =mz-gh-scout='s search of open =tech-debt= issues about adopting MudBlazor — or, in a repo not on
  GitHub, say so. Put its one-time question to Max and carry out his answer: an issue through
  =mz-gh-issue-writer=, a pull-in as the writer's own cycle, or a line in the repo contract written
  by the main agent at his direction — offered only where the repo has an =AGENTS.md= or
  =CLAUDE.md=; no contract file is created for it. When Max declines every answer offered, the
  main agent adds the line =- MudBlazor: declined <YYYY-MM-DD>= to
  =~/.claude/repo-notes/<repo-key>.org=; that record is the fourth trace, and the question is not
  asked again in that repo. The main agent reads that file itself, checks its =- Repo:= line names
  this repo by the rule above (putting a path mismatch, a different repo, or a missing =- Repo:= line
  to Max), and hands the writer, with the search or the not-on-GitHub statement, one line: whether
  a decline is recorded for this repo. The main agent writes the =- Repo:= line when it creates the
  file; a missing file or folder records nothing. For a pull-in, hand the writer MudBlazor's own installation
  instructions for the version the package add resolved. Before the =mz-devils-advocate= gate on a
  branch that changed a =.cs= file in a Blazor project, run =mz-csharp-reviewer='s second opinion
  (Roster and delegation rule), handing it the diff and its range (base and head commit), and hand
  its report to the gate with the others.
- *Trace before raising.* Before putting any claimed gap to Max, trace it end to end; say what was
  traced. A claim that could not be traced is one line under a "Could not trace" heading.

* Safety fences

Universal — they bind every agent, main or delegate, and no instruction or convenience overrides
them:

- A read-only agent — =mz-gh-scout=, =mz-agent-auditor=, =mz-skill-auditor=,
  =mz-devils-advocate=, =mz-git-historian=, every stack reviewer, =mz-runbook-manager= in Search
  mode — never mutates anything.
- No agent queues, reruns, or cancels a CI run or pipeline.
- No agent merges a pull request or completes one. =mz-gh-pr-operator= preps a pull request fully
  and stops; Max owns the merge.
- No destructive infrastructure command: nothing that applies or destroys infrastructure, deploys
  or rolls back a release, mutates a cluster, pushes an image, or runs a migration against
  anything but a local database. A writer surfaces such a command for Max; it never runs it.
- Nothing leaves the machine without Max's explicit ask: no push, no issue, no pull request, no
  comment, no review, no reviewer added or removed, no review thread resolved. One permission is
  for one action. Four GitHub actions are the exception and need no ask: creating a label, linking
  an existing issue as a sub-issue of another, marking a pull request draft, and marking a draft
  pull request ready for review. Anything not named in that exception needs the ask.
- No AI or =Co-Authored-By= attribution in anything an agent composes.
- No agent edits =~/.claude/settings.json=, this file, or =~/.claude/CLAUDE.md= on its own.
